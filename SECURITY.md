# Security

## Operational boundary

This repository contains executable orchestration code. Review changes before running it with authenticated Codex, Dreamina, Ark, or TOS accounts.

- During local preparation, the deterministic parent uses trusted local FFmpeg to create a bounded set of timestamped source frames. The configured Codex model receives those sampled frames, the ordered reference images and structured Job JSON; the source video itself is not attached to that prompt turn. These images and JSON still leave the machine for inference.
- The prompt turn runs with `CODEX_EXEC_SERVER_URL=none` and records `execution_environment: none`: no execution/filesystem environment is registered, so it receives no shell, patch, file-reading, permission-request or network tools. It cannot persist an artifact; the parent validates the returned structured prompt string and alone writes `prompt.txt`.
- Prompt-node authentication lives in the stable external, instruction-free, file-auth `$VIDEO_REPLACER_STATE_DIR/codex-node-home/`. The Agent initializes it only through the launcher's `setup login-codex-node` flow, while the user completes account authorization in Codex's protected interface. Setup does not copy credentials from the outer Agent on every prompt run. Doctor and production use the exact same home, which must contain no `AGENTS.md`, rules, skills, plugins, MCP configuration, hooks or other user configuration. Every use requires the bounded strict file-auth schema: the ChatGPT auth mode, null API-key field, exact required token fields, valid ID-token shape, nonempty access/refresh/account values, a timezone-aware refresh timestamp, constrained optional identity data, and no alternate credential field.
- An explicit node login can repair a malformed stale `auth.json` only when it is a regular file and the locked home has already passed its independent path, structure and permission/ACL checks. The implementation rechecks the exact file identity before unlinking only that file, preserves a valid auth file for Codex to replace or revoke, and runs strict validation after login. Links, nonregular entries, unsafe homes and identity changes fail before Codex starts. Error and status output never includes token material.
- READY includes two local zero-tool wire phases under the same stable node-home lock. Required check `codex-wire` starts the exact production prompt command with a synthetic image and an unauthenticated loopback Responses mock (`requires_openai_auth=false`); it requires empty top-level and nested/additional tool surfaces, no multi-agent host hints, an attached image, and no authorization/API-key header. Required check `codex-file-auth-wire` uses the same command and home with a loopback mock configured as `requires_openai_auth=true`; it requires the same zero-tool image surface and exactly one Bearer authorization handshake. It strictly validates stable `auth.json`, computes both access-token and captured-Bearer SHA-256 values in memory, and uses `hmac.compare_digest` to prove equality. Raw token and header values are neither retained nor logged. Each mock captures one `/v1/responses` request and stops it with HTTP 418. Managed/system MCP, hook, tool or multi-agent reinjection that reaches either wire surface fails READY.
- All prompt-node Codex processes are serialized. This is a credential-integrity boundary: concurrent Jobs must not race while refreshing or rewriting the shared file-auth tokens.
- Remote video submission occurs only through an explicit `--confirm-paid` command and can consume credits or incur charges.
- Ark credentials are read only by the Ark adapter after that paid Gate. Dreamina, Codex, FFmpeg, OpenScrub and dependency installers receive credential-minimized environments.
- Runtime media belongs under ignored `workspace/`, `outputs/` and `assets/reference-images/` paths. Recovery state belongs outside the repository.
- Agent setup stores only non-secret profile, code-contract, tool identity/path, capability and Doctor evidence in ignored `.video-replacer/setup.json`. On Windows the Codex identity includes the exact release's proved `official_sha256` and `official_release_tag`; it never stores a universal allowlist digest. CLI authentication remains in the provider store. The public setup Gate does not accept environment-only API credentials as persistent READY.
- The repository Dreamina installer downloads one pinned official binary URL, verifies its reviewed SHA-256, and installs the executable under ignored `.video-replacer/bin/`. It separately validates repository-pinned official release metadata and atomically creates the current user's `~/.dreamina_cli/version.json` (on Windows, `%USERPROFILE%\.dreamina_cli\version.json`) only when that provider file is absent, before its bounded real `dreamina version` check. Existing schema-valid provider metadata is preserved; malformed, nonregular or link-like metadata fails closed. That file contains non-sensitive version/update metadata; credential files remain untouched. The installer never pipes remote text into a shell, edits PATH or installs a global Agent skill.
- Dreamina OAuth/device login is launched only through the current platform launcher's `setup login-dreamina` command. Agents must not execute the provider binary directly.
- Do not commit `.env`, account data, cookies, task ledgers, signed URLs, media, generated prompts or outputs.

## Native Windows boundary

Windows support targets native Windows 11 x64, the root `.cmd` entrypoints, and OpenAI's modern native standalone `codex.exe` package. The setup Gate rejects npm `codex.cmd` / `codex.ps1` wrappers so batch-file shell reparsing cannot enter the prompt-node trust boundary. A `.exe` suffix alone is not an authenticity signal.

Before the repository invokes Windows Codex, it resolves the canonical `packages/standalone/releases/<version>-x86_64-pc-windows-msvc/bin/codex.exe` and rejects legacy/nonofficial layouts, missing or reparse-linked required entries, and invalid `codex-package.json` metadata. It derives the version from that validated package rather than executing an unverified binary. The verifier then permits only the exact HTTPS URL `https://releases.openai.com/codex/releases/<version>/release.json`, requires its tag to match that package and exactly one `codex-x86_64-pc-windows-msvc.exe` asset, and compares the manifest SHA-256 with a stable-file hash of the actual executable. Redirects outside the exact official host/path, duplicate or malformed metadata, changed files and digest mismatches fail closed.

Node login, Doctor/version/model checks and each production prompt launch all pass this Gate before executing Codex. Each live setup status refetches the exact-version release manifest and rehashes the binary, then compares the resulting `official_sha256` and `official_release_tag` with setup identity. It does not trust a prior setup record or fixed-version digest. If the exact official manifest is unavailable offline, provenance cannot be proved and READY fails closed.

WSL and Git Bash are outside the public Windows lane. The launcher does not require a permanent PowerShell execution-policy change. Keep the clone at its user-selected path, including paths with spaces or Chinese characters, and pass paths as individual process arguments rather than shell-concatenated text.

Every Windows entrypoint resolves one immutable state root through the Known Folder API using the real current-user token: `FOLDERID_LocalAppData/video-replacer`. It does not derive trust from `LOCALAPPDATA` or other environment text. `VIDEO_REPLACER_STATE_DIR` may be absent or may restate that exact canonical path; any redirect to a different parent fails closed. The root and node home must resolve on a local fixed drive. UNC paths, mapped drives, non-fixed drives and every reparse-point component are rejected. The node-home directory, `auth.json` and `.video-replacer-auth.lock` are owned by the current user and use inheritance-protected DACLs containing only two full-control allow ACEs: the current user and `SYSTEM`. Setup applies this boundary; login, Doctor and production validate the live native owner/DACL before credential use. POSIX retains its absolute override and XDG state semantics.

On native Windows, the outer repository Agent and deterministic workflow may use Codex's official `windows.sandbox="elevated"` mode. Despite its name, this is not an administrator workflow process: after its one-time administrator-approved setup, Codex commands run under dedicated lower-privilege sandbox users. The inner prompt turn is a different boundary: it points at the stable external node-only file-auth `CODEX_HOME`, sets `CODEX_EXEC_SERVER_URL=none`, and does not depend on a sandbox execution environment or create a second elevated sandbox/home. It receives parent-attached images and JSON without execution or filesystem tools. Codex's outer `unelevated` mode remains a weaker fallback and receives separate compatibility coverage in this release contract. A trusted system dependency install may use one explicit, narrowly scoped UAC/administrator process, but that separate process must end before READY verification and must not leave files or credentials usable only by an administrator. Never run a paid submission merely to test either sandbox mode. A public Windows release additionally requires the fresh-user, OAuth, second-session, prepare-only, and sandbox evidence in [RELEASE.md](RELEASE.md); CI alone is not security evidence for those boundaries.

The model request captured in each wire phase is routed to the loopback mock and rejected with HTTP 418 before any model response or inference. The first request carries no auth; the second performs the authenticated local handshake. Both use only a synthetic image and contain no video-backend operation or paid command. This attestation does not make a claim about unrelated network activity by the process. READY depends on both captured surfaces and the in-memory file-auth equality proof.

Before any public release, copy the reviewed payload without `.git` into an independent clean-root Git repository; a branch inside the legacy repository is insufficient because old refs remain visible. In a fresh clone of that independent candidate, run `.venv/bin/python tools/release_audit.py --history` and `./video-replacer-test` on macOS, or `.\.venv\Scripts\python.exe .\tools\release_audit.py --history` and `.\video-replacer-test.cmd` on Windows.

## Mosaic limitation

`mosaic_required` invokes a fixed best-effort face mosaic pipeline. The workflow verifies process success and output existence; it does not verify complete face coverage or irreversible de-identification. Mosaic patterns may retain recoverable information. Do not rely on this mode for regulated anonymization or high-risk identity protection.

## Paid execution

Approval is batch-specific and hash-bound. Changing media, references, profile, upload-preparation evidence or preflight state invalidates the prior checkpoint. An uncertain remote submission is resumed from the external ledger; it is not automatically recreated.

The default daily paid limit is one new submission. It is a guardrail, not a budget system. Monitor the backend account and never expose paid commands through unattended automation.

## Reporting a vulnerability

Do not disclose credentials, private media or active signed URLs in a public issue. After the GitHub repository is published, use its private security-advisory channel. Until then, contact the maintainer through a private channel already known to you.
